Why CPU-target autoscaling is structurally dead

July 2026 · 9 min · aws, autoscaling, node

We had an autoscaling policy targeting 40% average CPU on a service that, at full saturation, could not report much above 25%. The policy was not conservative. It was mathematically incapable of triggering.

The failure, concretely

During a traffic burst the fleet sat pinned at min_capacity while the load balancer shed the overflow: 12,243 gateway timeouts in a single metric bucket. Application 5xx stayed at zero the whole time, because the app never errored. It just stopped answering. Every dashboard that watched error rate looked green while users watched spinners.

The root cause is the same arithmetic from the resize story: a single-threaded runtime on an N-vCPU task caps application CPU near 1/N. A 40% target against a ~25% ceiling is a policy that can never fire, on any traffic, ever. No amount of tuning the threshold fixes a broken denominator.

Scale on the resource that actually saturates

For a single-threaded server the scarce resource is the event loop, and the load on it is proportional to request rate. So we scale on ALBRequestCountPerTarget: it tracks the thing that saturates, it is independent of task size, and it moves the moment traffic moves instead of after CPU averages catch up. CPU stays as a secondary policy for pathological cases.

Judge saturation by event-loop lag, not CPU

The metric that told the truth throughout was event-loop lag. We run a lightweight runtime-health sampler in every task that emits loop lag percentiles, GC pause stats, and the heap limit the runtime actually got. When the loop’s p99 climbs, the service is saturated, whatever CPU says.

Takeaways

1. Before trusting any CPU percentage, ask what the process can physically consume.
2. An autoscaling policy needs a proof it can fire; alarm on “time at min_capacity during burst” if you keep one you are unsure about.
3. ALB 5xx and target 5xx are different metrics; a healthy-looking app can still be shedding thousands of requests at the balancer.
