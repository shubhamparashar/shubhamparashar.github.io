Cutting a Fargate fleet’s cost 41% without touching latency

July 2026 · 12 min · aws, fargate, cost

Our GraphQL service ran on Fargate tasks sized 4 vCPU each, and the fleet averaged 6–8% CPU. The obvious reading is “plenty of headroom.” The correct reading is “we are paying for cores the runtime physically cannot use.”

A single-threaded runtime cannot saturate a multi-vCPU task

A Node process runs application code on one thread. On an N-vCPU task, application CPU tops out near 1/N:

Task sizeMax reportable CPU at full saturation
1 vCPU~100%
2 vCPU~50%
4 vCPU~25%

So our measured 6–8% average with ~20% peaks was not headroom. It was a saturated JS thread hiding behind a denominator. One caveat we measured before acting: V8 also runs GC and compiler threads on other cores, so the process as a whole can briefly exceed 1/N. That auxiliary load is real and it is what you delete when you cut cores, so budget for it instead of assuming a free resize.

What we actually changed

Three moves, one commit each:

1. Sized tasks to what the runtime can use. One core for the work thread plus headroom for GC and the libuv pool. We also learned the hard way that os.availableParallelism() reads the CPU affinity mask, not the container quota, so the thread pool does not shrink when the task does. Read the cgroup (or on Fargate, the task metadata endpoint) if you want the truth.

2. Moved heap flags in the same commit as memory. --max-old-space-size is an absolute number, not a percentage of the container limit. Shrink the container without shrinking the flag and the OOM killer will explain the relationship to you at 3am.

3. Verified the deployed task actually got the sizing. An edited config that never reached a running task looks identical to a successful change. We emit the runtime’s own view (v8.getHeapStatistics().heap_size_limit, cgroup CPU quota) as gauges on every boot.

The 7-day vigil

Averages hide resize regressions; tails reveal them. Instead of a smoke test and a prayer, we captured a pre-change baseline (p99 latency, event-loop lag, GC pause distribution, 5xx counts) and ran an automated sweep every 45 minutes for a week, comparing live signals against the baseline and paging on divergence. 234 checks, 0 anomalies, p99 flat.

Result: 41% cheaper per task, latency unchanged. The bill went down because the mental model changed, not because anyone “optimized” code.
